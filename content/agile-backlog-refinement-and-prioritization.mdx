When every stakeholder claims their feature request is "urgent and critical," prioritization collapses unless governed by quantitative scoring models. A strong Business Analyst serves as the objective filter that protects engineering throughput while maximizing delivered business value.

## 1. The MoSCoW Method: Structuring Releases

For fixed-scope releases, **MoSCoW** establishes clear operational thresholds:

- **Must Have**: Non-negotiable core functionality (e.g., PCI-compliant payment checkout). If omitted, the release is invalid.
- **Should Have**: High-value enhancements that have viable manual workarounds in Phase 1 (e.g., 1-click refund triggers).
- **Could Have**: Desirable quality-of-life additions implemented only if sprint velocity permits (e.g., custom dashboard themes).
- **Won't Have (This Time)**: Explicitly deferred items preventing scope creep.

## 2. The RICE Scoring Framework: Data-Driven Backlog Ranking

When evaluating competing feature ideas across diverse departments, the **RICE** model produces an objective score:

```
RICE Score = (Reach × Impact × Confidence) / Effort
```

1. **Reach**: Number of users impacted over a defined cadence (e.g., 5,000 active MAU).
2. **Impact**: Estimated user outcome (3 = Massive, 2 = High, 1 = Medium, 0.5 = Low).
3. **Confidence**: Confidence percentage based on user telemetry and research (100% = High, 80% = Medium, 50% = Speculative).
4. **Effort**: Engineering person-months or story point estimates.

## 3. Leading Effective Backlog Grooming Sessions

- **Pre-grooming Triage**: Refine acceptance criteria before introducing tickets to developers.
- **Slicing Large Epics**: Break down user stories that exceed 8 story points into smaller vertical slices.
- **Definition of Ready (DoR)**: Enforce strict entry gates before any story enters an active sprint.
